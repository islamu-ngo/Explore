# Full Property Update Sub-DTO Pattern - Phase 1 Inventory

Last Updated: 2026-06-28 Europe/Brussels

## Purpose
This inventory is the source of truth for the first implementation slice. It prevents the update migration from becoming a blind DTO rewrite by recording the existing API contract, CQRS handlers, authorization posture, cache invalidation, concurrency, transaction, audit, and generated-client foundations before any product code is changed.

The approved target remains:
- property updates use `PATCH /api/{resource}/{id}`;
- route ID is authoritative;
- body IDs are removed from update DTOs;
- wrapper DTOs expose nullable logical groups;
- nullable or clearable fields inside groups use `OptionalUpdate<T>`;
- one command and one handler remain per update-eligible entity;
- repositories return entities and handlers own mapping;
- domain actions remain separate commands.

## Domain Actions To Keep Separate
Do not convert these into property update groups unless a future CTO-level decision explicitly changes the domain model. These commands express business processes, not editable property state. They retain their own request DTOs, authorization actions, audit behavior, side effects, cache invalidation, and tests.

| Action family | Current examples | Why it stays a command | Required governance |
|---|---|---|---|
| Event/session lifecycle | `PublishEventCommand`, `ArchiveEventCommand`, `CancelEventCommand`; future schedule/complete lifecycle commands | These transitions enforce readiness, status, notifications, visibility, and cache/list semantics. Treating them as `Status` property writes would bypass lifecycle invariants. | Keep explicit resource action authorization, readiness validation, audit/logging, and detail/list/HAL cache invalidation. |
| Moderation and redaction | `ModerateEventCommand`, `UnmoderateEventCommand`, `HeavyRedactEventCommand` | Moderation uses explicit Cerbos/local actions and safe audit metadata. Heavy redaction has irreversible storage deletion and attendee notification side effects. | Keep `moderate-light`, `moderate-heavy`, `unmoderate` authorization, fail-closed HAL affordances, safe logging, audit metadata, and no raw moderated content exposure. |
| Approval and verification decisions | `UpdateOrganizationApprovalStatusCommand`, `UpdateGroupApprovalStatusCommand` | Approval changes are admin governance decisions, not ordinary organizer-editable details. | Either retain as dedicated commands or migrate only as admin-only action groups with group authorization and audit. Initial disposition is keep separate. |
| Role, member, and ownership processes | `AssignEventRoleCommand`, `AssignEventRoleByEmailCommand`, `RevokeEventRoleAssignmentCommand`, `TransferEventOwnershipCommand`, `UpdateEventRoleAssignmentWindowCommand`, group/organization member role commands | These mutate relationship rows, validate authority windows, enforce membership/ownership invariants, and produce audit events. | Keep dedicated commands, event/member-specific authorization actions, transaction boundaries where multiple assignments change, and audit logs. |
| Template sync and projection maintenance | `ApplyEventTemplateSyncCommand`, `ApplyEventSessionTemplateSyncCommand`, custom-property projection rebuild/drain operations | Sync applies a plan, provenance/concurrency checks, projection behavior, and multi-row writes. | Keep command-specific validation, UoW/transaction use, audit logs, and template/projection cache invalidation. |
| Purge, delete, reset, and destructive admin operations | `PurgeCustomPropertyDefinitionCommand`, `PurgeEventCustomPropertyDefinitionCommand`, `PurgeEventSessionCustomPropertyDefinitionCommand`, `ResetSettingCommand` | These are destructive or governance-controlled operations with confirmation and side effects. | Keep admin authorization, explicit confirmation DTOs, audit logs, and no property-update route aliases. |
| Secret, token, and credential rotation | `RotateKeycloakClientSecretCommand`; future API key/token rotation commands | Rotation interacts with external/deployment-managed secret ownership and must not be represented as a writable secret property. | Keep safe diagnostics, no secret logging, operator-instruction paths, and separate authorization. |
| Upload/session workflows | Storage upload session create/proxy/finalize/cancel flows | Upload sessions bind user, size, content type, provider policy, and SSRF-sensitive server-side proxy decisions. | Keep session-bound command/endpoints, BFF/API boundary controls, and no client-controlled provider URLs or object keys. |
| Settings batch, governance, and onboarding flows | `UpdateSettingBatchDto` flows, setup/onboarding/provisioning commands, managed-provider provisioning | These are administrative processes with lock checks, tenant boundary setup, or multiple aggregate writes. | Keep command-specific authorization, tenant isolation, configuration history, transaction boundaries, and API changelog entries. |

- `OptionalUpdate<T>` implemented in the approved Application model location, build-verified, and covered by focused Application unit tests;

- group-level authorization helper or local handler pattern chosen;
- User cache and transaction test plan written;
- OpenAPI/client regeneration workflow validated on a real contract change.
