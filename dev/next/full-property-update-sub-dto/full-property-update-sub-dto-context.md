## Key Decisions
- Use `PATCH /api/{resource}/{id}` for property updates.
- Route ID is authoritative; body IDs are removed.
- Do not maintain backward compatibility for old broad `PUT` property update bodies.
- Use wrapper DTOs with nullable logical groups.
- Use `OptionalUpdate<T>(bool HasValue, T? Value)` only for nullable/clearable fields.
- Present group with no actual operation fails validation.
- Keep one command and one handler per update-eligible entity.
- Enforce one private `ApplyX` method per group.
- Add group-level authorization for mixed-authority groups.
- Add optimistic concurrency for major aggregates, preferring the existing `Guid ConcurrencyStamp`/`IConcurrencyAware` convention where it fits and preserving documented `Version`/provider-specific exceptions.
- Use strong `If-Match` at API boundary and pass the parsed expected concurrency value into commands.
- Multi-repository updates require explicit transaction/unit-of-work boundaries.
- Cache invalidation matrices are required before implementation per entity.
- Sensitive groups require audit handling or explicit exclusion.
- Domain actions remain separate commands.

## Constraints And Rules To Remember
- Repositories return entities only; mapping belongs in handlers.
- Validators are manually instantiated; no DI-injected validators.
- Write endpoints remain `[Authorize]`.
- HAL links are the UI source of truth for mutation affordances.
- Link/junction writes go through repositories, not navigation collection mutation.
- Tenant ID is never trusted from update bodies.
- Cross-tenant relationship IDs fail closed.
- All new/touched files need two `ABOUTME` lines.
- Use `Guid` for aggregates, `int` for lookups, `long` for version/cursor/large sizes.
- No compatibility shims unless the user explicitly reverses the current no-backward-compatibility decision.
