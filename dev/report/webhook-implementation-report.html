ISLAMU Event · extensive implementation report · 13 July 2026

Webhooks that fail safely.

A repository-grounded assessment of the existing Local and Svix delivery engine, its verified transaction gaps, the five-scope administration target, and the protocol required before an ERP invoice integration can make financial guarantees.

Release build: green Current delivery: at-least-once Local: default Svix: optional Research: converged
01 · Decision

Keep both providers. Fix guarantees above the transport.

Keep the existing canonical message ledger and provider architecture. Local remains the self-hosting baseline. Svix remains optional for managed delivery and recovery. Do not promise exactly-once effects from either transport. Repair inbound processing, provider binding, ownership, and business idempotency at the application boundary.

02 · Reality

This is not greenfield.

The repository already contains a substantial webhook subsystem: a canonical event catalog and envelope, durable application messages, five provider modes, endpoint and subscription administration, Local leasing and retry, Svix App Portal delegation, signed incoming intake, tenant-scoped duplicate ledgers, metrics, health checks, HAL resources, and a Blazor management panel. The correct work is hardening and extending, not replacing. [S1-S4]

Canonical wire contract

Contract boundary

This is signed application/json, not CloudEvents. Additive payload fields are compatible. Removing, repurposing, or changing a field type requires a new event type or parallel schema version. Add CloudEvents later only as an explicit opt-in profile with tests. [S4][S16]

03 · Providers

Shared semantics, different operating models.

Default · Local

Self-contained control

  • Durable attempts, leases, retry, stale-lease recovery, manual retry.
  • Svix-compatible raw-body signing headers.
  • SSRF policy checks every DNS result and keeps metadata immutable-blocked.
  • Bounded timeouts, no redirects, redacted telemetry.
  • Platform team owns delivery operations and recovery quality.
Optional · Svix

Delegated operations

  • Managed attempts, retry, disablement, recovery, and App Portal.
  • Stable message ID across retries and raw-body signatures.
  • API token remains server-side.
  • Provider-specific ordering, retention, features, and tier limits.
  • Application still owns canonical messages and provider links.

Verified binding weakness, not a proven exploit

ExternalProviderAppId is caller supplied and used as the Svix application UID. Research proved the absence of a durable tenant/consumer ownership binding, but did not prove cross-tenant exploitability. Create the provider app server-side, persist an immutable binding, verify provider metadata, and derive portal capabilities from policy rather than request fields. [S7]

04 · Incoming

Strong verification, unsafe resume boundary.

Implemented

Authenticate first

Bounded raw body, signature verification before JSON parsing, timestamp tolerance, fixed-time comparison, rotation overlap.

Implemented

Deduplicate

Tenant/provider unique message and idempotency keys; duplicates are acknowledged without rerunning commands.

Verified defect

Cannot resume

Capture commits before command execution. A crash can leave Verified and cause future duplicates to skip the effect.

Verified → Processing(lease + fence) → Processed | RetryDue | DeadLettered → HAL-gated redrive

The fix belongs in a durable worker, not another controller retry. Claim with database time, fence state transitions, recover stale leases, store bounded failures, and expose safe operator redrive. Lock the defect with a crash-after-capture acceptance test. [S5][S19]

05 · Financial

One business operation, never one transport guess.

Neither Local nor Svix can make an arbitrary ERP call exactly once. An ambiguous remote outcome must be reconciled before resend.

The future examples ticket.order.completed and isl_order_998412 do not exist in the repository. The architecture below is the admission standard for a future invoice integration, not a description of current capability. [S8-S11]

Required state machine

RECEIVED → AUTHENTICATED → CANONICALIZED → DUPLICATE | PAYLOAD_CONFLICT | PENDING
PENDING → LEASED(fence) → RECONCILING | ATTEMPT_PREPARED → REMOTE_PENDING | ISSUED | OUTCOME_UNKNOWN | RETRY_DUE | MANUAL_RECONCILIATION | CORRECTION_REQUIRED
REST

Stable key plus external reference

Persist ATTEMPT_PREPARED before send. Treat timeout/reset/ambiguous server failure as OUTCOME_UNKNOWN. A generic Idempotency-Key header is not a universal guarantee; test the ERP's semantics and retention.

JSON-RPC

Correlation is not deduplication

Use a normal request, never a notification/batch. Place a stable external reference and explicit idempotency key in params. Require a lookup/status method. Persist a unique correlation ID per attempt.

ERP admission gate

Prove durable same-key behavior and retention, external-reference uniqueness under racing creates, reliable lookup, async status/restart semantics, and correction primitives. If a critical capability is absent, disable automatic ambiguous retries or automated production issuance. Issued invoices are immutable; changes create linked corrections under qualified fiscal review. [S8][S20-S23]

06 · Governance

Five scopes require ownership, not labels.

Instance currently owns provider configuration, while webhook business resources are tenant bounded. Organization and Group names do not create ownership ancestry, and ordinary User ownership is incomplete. Adding selectors before the data and policy model would create cosmetic scopes with unsafe expectations. [S12][S24]

Minimal enforceable model

{ TenantId, Kind: Tenant|Organization|Group|User, ScopeId }. Instance remains provider/configuration authority, not an ordinary tenant data owner. Validate membership in the tenant and the delegating principal's subtree. Snapshot owner scope onto messages and attempts. Keep settings inheritance/locks separate from object ownership.

ScopeRecommended authority
InstanceProviders, Local network/limits, Svix credentials/base URL, defaults/locks, health, global audit.
TenantConsumers, endpoints, subscriptions, bounded retention, tenant recovery and audit.
OrganizationExplicitly owned integrations and subtree evidence only when delegated.
GroupGroup-owned endpoints/subscriptions when delegated; no upward visibility.
UserPersonal integration resources only where policy explicitly allows.

HAL remains the only client action authority. Page guards may control reachability, but create/update/retry/rotate/portal buttons must come from API links, never local role or claim inspection. [S13][S14]

07 · Product

Move from a settings panel to an operations workspace.

The current Blazor panel safely supports core Local actions and Svix portal entry, but only inside single-tenant instance settings. It lacks multi-scope entry points, a complete attempt timeline, pagination/search, incoming redrive, and a generic audit browser. Preserve generated API clients, safe DTOs, and HAL gating. 08 · Security

Preserve the hard boundary. Close delegation gaps.

Preserve

Existing controls

  • Verify raw body before parsing.
  • Bound size/time and use fixed-time comparison.
  • Tenant filters fail closed.
  • Provider and endpoint secrets stay server-side.
  • Local blocks unsafe destinations and redirects.
  • HAL gates every action affordance.
Add

Required hardening

  • Immutable server-created provider application binding.
  • Policy-derived App Portal permissions.
  • Durable inbound leases and operator redrive.
  • Append-only admin audit separate from delivery data.
  • Inherited rate/retention/endpoint limits with locks.
  • Shared signature conformance fixtures.
09 · Operations

Page on threatened guarantees, not routine retries.

Measure

Queue depth, oldest age, inflight, retry/dead-letter/redrive, signature failure, provider readiness, unknown-outcome age, provider-link mismatch.

Alert

Sustained SLO burn, age threatening replay/retention, broad tenant impact, readiness loss, or growing reconciliation unknowns.

Diagnose

Bound dimensions. Never label metrics with URLs, IDs, payload/hash, secret reference, headers, signatures, body, or raw errors.

Candidate spans are webhook.incoming.verify, webhook.incoming.capture, webhook.outgoing.publish, and webhook.outgoing.deliver. Maintain separate runbooks for Local backlog/stale lease, Svix readiness/link reconciliation, signature rotation, inbound redrive, endpoint disablement, and financial unknown outcome. [S4][S17][S26]

11 · Roadmap

Reliability first. Operations second. Finance only after admission.

P0

Reliability and authority blockers

  1. Inbound processing leases, retry/dead-letter/redrive, crash tests.
  2. Server-bound Svix applications and policy-derived portal capabilities.
  3. Provider-send reconciliation and explicit unknown publication state.
  4. Typed owner scope and delegation before multi-scope UI.
P1

Operations and administration

  1. Incoming list/detail/redrive API, HAL, generated client, UI.
  2. Delivery timeline, pagination/search, safe details, admin audit.
  3. Metrics, spans, dashboards, SLOs, and runbooks.
  4. Provider capability matrix and configuration validation.
P2

Financial integration foundation

  1. Define versioned order event only when the ticketing domain exists.
  2. Implement ingress, operation, attempt, reconciliation ledgers.
  3. Run ERP admission harness against the selected ERP.
  4. Approve fiscal correction semantics with qualified review.
  5. Enable issuance only after the full failure matrix passes.
P3

Optional ecosystem work

  1. CloudEvents profile only if interoperability demand justifies it.
  2. Lower-scope ownership only where product policy needs it.
  3. Add provider capabilities individually, without forced parity.
