## 1. Executive Summary

This workstream is a controlled hardening program, not a generic cleanup. The target state is an explicit input contract for every untrusted boundary, with authoritative server-side validation, safe user-facing errors, predictable Blazor form UX, and narrowly scoped sanitization where the system intentionally accepts renderable markup.

The corrected architecture is:

1. API and Application are authoritative for command/query validation.
2. BFF endpoints validate BFF-only seams, proxy shape, antiforgery/compensating controls, upload/session headers, and token-boundary behavior.
3. Blazor Client performs responsive UX validation, accessibility support, server-error mapping, and HAL affordance display. It never becomes the security authority.
4. Sanitization is not a blanket middleware. Default defense against XSS is Razor/component output encoding plus context-aware encoding. Sanitizers are only introduced for approved rich-content seams with an explicit allowlist, tests, and ownership.
5. OpenAPI and generated clients are part of the implementation contract. Future implementation agents run the generation commands when contract changes require it; they do not ask the user to regenerate artifacts manually.

Bad patterns removed from this plan:

- Global or response-side sanitization filters.
- Validator auto-registration through DI.
- Business rules in controllers or Blazor components.
- Treating Blazor validation as sufficient security.
- `MudForm` standardization in conflict with local UI governance.
- Direct Application validator reuse from `Explore.Blazor.Client`.
- Asking the user to run required generation or verification steps on behalf of the implementation agent.

### Senior CTO Verdict And Correction

**Decision: Approve with required changes already applied to this rebaseline.** The architecture direction is correct only if future work stays matrix-backed and does not drift into broad cleanup. The remaining implementation must prioritize high-risk boundary rows, not another open-ended storage audit. Each slice must pick one row or tightly related endpoint family from `full-input-validation-sanitization-input-matrix.md`, update the row first, implement the smallest API/Application/BFF/Blazor correction, and record focused verification before moving on.

The corrected emphasis is:

1. **API/Application authority:** validate request/query/route/header/body shape at the API boundary, enforce semantic tenant/state/authorization rules in handlers/services, and keep controllers thin.
2. **BFF trust boundary:** validate only BFF-owned seams such as antiforgery, proxy/session/header/cookie/setup-secret behavior, and token isolation. Do not duplicate normal Application command validation in BFF code.
3. **Blazor UX and rendering safety:** use `EditForm`/`EditContext`, `ServerValidationErrorStore`, accessible summaries, HAL link affordance gating, normal Razor encoding, and reviewed raw-rendering allowlists. Blazor validation remains UX only.
4. **Sanitization discipline:** prefer output encoding. Use sanitizers only for an approved rich-content seam with a decision record, allowlist, and malicious payload tests. CSV/TSV formula neutralization and safe filename generation are export-specific sanitization, not a generic HTML sanitizer pattern.
5. **No audit-only work:** an audit task is complete only when it produces a matrix update, a contract decision, code/test changes, or a documented deferral with owner and rationale.

## 4. Non-Negotiable Constraints

These constraints override generic framework examples and external blog guidance.

1. Repositories return entities, never DTOs.
2. Application validators are manually instantiated. Do not register all validators in DI.
3. Use `ValidateAsync` for FluentValidation. Do not rely on ASP.NET automatic validation for FluentValidation rules, especially async rules.
4. Controllers stay thin. They bind requests, call MediatR/services, and return results.
5. Business and tenant-aware validation belongs in Application handlers/services or persistence constraints, not controllers or Blazor components.
6. API and BFF errors must use the canonical problem-details contract. Do not return ad hoc strings or leak raw input values.
7. GET endpoints are `[AllowAnonymous]`; write endpoints are `[Authorize]`, unless an existing documented exception applies.
8. HAL links are the single source of truth for UI action affordances. Blazor must gate Edit/Delete and similar actions by `_links` presence, not local role or claim checks.
9. Tokens stay server-side in the Blazor BFF. `Explore.Blazor.Client` must not receive bearer tokens.
10. Antiforgery is required for unsafe BFF form/API-post paths unless the route is one of the documented exceptions in `docs/SECURITY-MODEL.md` and has compensating controls covered by tests.
11. Prefer output encoding over sanitization. Add a sanitizer only for approved rich HTML or Markdown-to-HTML seams.
12. Never add global input mutation middleware or global HTML sanitization middleware.
13. Never sanitize by stripping arbitrary characters from identifiers or names without an explicit canonicalization rule. Reject invalid input or canonicalize in a named normalizer/handler step.
14. Never write implementation tasks that ask the user to regenerate OpenAPI clients, run required tests, or finish mandatory verification manually.

## 5. Architecture Decisions

### A1. Server-Side Validation Is Authoritative

All API request bodies, query objects, route IDs, headers, and uploaded metadata are validated on the server. Client-side validation improves user feedback but has no security authority.

Application validators enforce command/query syntax and cross-field shape. Handlers enforce semantic checks that need repositories, authorization context, tenant context, clock, feature state, or idempotency state.

### A2. API Model Binding Normalizes Transport Errors Only

The API layer owns:

- Unknown JSON member rejection.
- Malformed JSON and model-binding errors.
- Required route/query/body shape errors.
- Canonical validation problem details.

The API layer does not own domain or tenant rules.

### A3. BFF Validation Protects BFF-Only Seams

Blazor Server/BFF endpoints own:

- Proxy route and request shape validation.
- Upload-session header and cookie contracts.
- Setup-secret and operational endpoint input shape.
- Antiforgery or documented compensating control tests.
- Token-boundary checks proving tokens are not exposed to the browser.

BFF code should not duplicate Application command validators for normal API commands. It should pass canonical DTOs through generated clients/services and map API problem details back into Blazor forms.

### A4. Blazor Validation Is UX, Accessibility, and Error Mapping

Blazor Client owns:

- Immediate field-level feedback.
- Preventing duplicate submit UX.
- Accessible validation summaries and focus behavior.
- Mapping API field errors into `EditContext` through `ServerValidationErrorStore`.
- Hiding actions when HAL links are absent.

Blazor Client must not:

- Become the only validation layer.
- Inspect local roles/claims to decide affordances.
- Directly reference Application-layer validators.
- Introduce `MudForm` as the standard pattern.

### A5. Canonicalization Is Explicit and Separate From Validation

Validators may compare normalized values for validation, but they should not silently mutate commands or request DTOs. Persistent canonicalization belongs in named normalizers, handlers, value objects, or persistence constraints so behavior is testable and auditable.

Examples:

- Trim display names before persistence only through an explicit handler/normalizer step.
- Normalize emails consistently before uniqueness checks if the product contract requires it.
- Generate safe storage object names instead of trusting user-supplied filenames.
- Preserve user-visible text when trimming would alter meaning unless the product contract explicitly says otherwise.

### A6. Sanitization Is Content-Type Specific

Most input is not sanitized. It is validated, stored as data, and encoded on output.

Sanitization is only appropriate for approved renderable content such as rich HTML or Markdown-derived HTML. Each approved seam needs:

- A decision record.
- Sanitizer library/package and version.
- Allowlist of elements, attributes, URI schemes, and protocols.
- Tests for script, event handler, dangerous URL, malformed HTML, and style injection payloads.
- Clear ownership for server-side and display-side behavior.

Do not sanitize structured data, identifiers, URLs, filenames, object keys, or JSON by running them through an HTML sanitizer.

### A7. Idempotency Is Part Of Input Validation

Idempotency keys and fingerprints validate retry intent. Behavior must align with the repo contract and be intentionally compared against IETF draft semantics:

- Same key + same fingerprint may replay the stored result after completion.
- Same key + different fingerprint is rejected as the repo's current `409 idempotency_key_reuse` contract. The current IETF draft examples use `422` for this case; changing status code would be an API contract migration requiring docs, OpenAPI/client review, and compatibility handling.
- Same key while the original request is still in progress is a `409` conflict or a documented pending response.
- Expiry behavior is explicit and tested.

### A8. Generated Artifacts Are Implementation-Owned

When an API contract changes, the implementation agent runs the documented commands to regenerate OpenAPI and API client artifacts, reviews the diff, and verifies generated clients compile. Asking the user to regenerate the client is not an acceptable task.

## 9. Security, Authorization, Privacy, And Abuse Controls

Security posture:

- Treat every browser, API client, BFF request, webhook, header, cookie, query string, route segment, uploaded filename, MIME type, storage metadata value, idempotency key, and generated callback/continuation URL as untrusted.
- Validate before side effects.
- Authorize before exposing tenant data or performing mutations.
- Use tenant predicates and ownership checks for IDs supplied by clients.
- Return safe, stable validation errors. Do not echo secrets or raw rich content.
- Encode on output by default.
- Sanitize only approved renderable content.

Privacy posture:

- Avoid logging raw validation payloads.
- Redact setup secrets, tokens, cookies, email verification tokens, upload object keys, user-supplied filenames where sensitive, and rich content bodies.
- Keep validation metrics low-cardinality.

Abuse posture:

- Enforce size and count limits.
- Validate pagination cursors, date ranges, search strings, and filter combinations.
- Preserve idempotency protections for retried writes.
- Avoid expensive sanitizer/parser work before cheap size checks.

## 10. Multi-Tenancy, Federation, Localization, Accessibility, And Product

Multi-tenancy:

- Every tenant-bound ID supplied by a client must be resolved through tenant-aware queries or ownership checks.
- Validation failures should not reveal whether a resource exists in another tenant.

Federation:

- Federation inputs are external trust boundaries. Apply the same validation/sanitization rules to federation payloads, signatures, IDs, URLs, and callbacks.
- Do not trust remote display names, summaries, URLs, or HTML.

Localization:

- Validation message keys should stay stable. User-facing text can be localized later, but field keys and machine-readable codes must not drift casually.
- Avoid culture-sensitive parsing without explicit culture rules.

Accessibility:

- Blazor validation must expose errors through accessible summaries/messages.
- Error focus behavior must be predictable.
- Do not rely on color alone to communicate invalid state.

Product:

- Do not degrade authoring UX by stripping meaningful text silently.
- Prefer clear rejection messages over hidden mutation.
- Rich-content support is a product decision with a security cost, not a default.

## 14. Research Evidence Summary

Tavily MCP research:

- OWASP Input Validation Cheat Sheet: validate all untrusted input, use syntactic and semantic validation, prefer allowlists, and do not treat input validation as the primary XSS defense.
- OWASP Cross-Site Scripting Prevention Cheat Sheet: use framework output encoding and context-aware encoding; sanitization is needed for safe HTML, but global/interceptor-style approaches are fragile.
- OWASP File Upload Cheat Sheet: validate extension, content type, signature, filename safety, size, storage location, and authorization; treat client-provided `Content-Type` as spoofable.
- OWASP Logging Cheat Sheet: validate/sanitize/encode event data before logging and avoid logging sensitive data.
- IETF HTTPAPI Idempotency-Key draft: idempotency keys protect retried POST/PATCH requests; the draft examples use same-fingerprint replay, 422 for key reuse with a different payload, and 409 for concurrent in-progress retries. This repo currently locks different-payload reuse to `409 idempotency_key_reuse`; keep that as a deliberate API contract unless a migration is planned.
- 2026-07-04 continuation notes: fresh Tavily OWASP eval/DOM-sink and API input-validation search/research attempts returned usage-limit status `432`, so those slices did not add new Tavily evidence beyond the previously incorporated OWASP/IETF guidance.

Context7 MCP documentation:

- ASP.NET Core docs support the existing use of `[ApiController]`, automatic 400 `ValidationProblemDetails` for model-validation failures, `InvalidModelStateResponseFactory`, `ProblemDetails`, Blazor `EditContext`, `ValidationMessageStore`, antiforgery, and secure file-upload validation. File upload examples treat uploaded filenames as untrusted, HTML-encode names for display, enforce size/count limits, and use trusted storage names.
- ASP.NET Core Blazor JS interop docs support importing ES modules and invoking module functions through `IJSObjectReference`; use JS modules for browser actions instead of global script execution.
- FluentValidation docs support manual validation and `ValidateAsync`; automatic MVC validation is not suitable for async rules and conflicts with this repo's manual-validator invariant.
- MudBlazor docs show generic `MudForm` support, but this repo's UI governance is more specific and authoritative for this codebase.
