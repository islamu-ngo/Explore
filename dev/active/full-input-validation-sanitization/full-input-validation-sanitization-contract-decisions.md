# Full User Input Validation & Sanitization Contract Decisions

Last Updated: 2026-07-04 Europe/Brussels

## Purpose

This file is the decision log for `full-input-validation-sanitization-plan.md`. Implementation has already started in several slices, so future work must keep any touched decision accepted, deferred with rationale, or explicitly escalated before editing the matching seam.

Current status: Contract lock is current through the 2026-07-04 Senior CTO rebaseline update. All decisions D-001 through D-030 are accepted and ready for implementation/test work.

Decision status values:

- `Pending` — no decision yet.
- `Needs design` — direction known, but implementation shape is unresolved.
- `Accepted` — contract locked; implementation may proceed.
- `Deferred` — explicitly out of this release slice with rationale.

## Decision Log

| ID | Decision area | Locked contract | Status | Owner | Tests to lock behavior |
|---|---|---|---|---|---|
| D-001 | Automatic `[ApiController]` model-state failures | Normalize automatic model-state failures into the repository API ProblemDetails contract: HTTP 400, `application/problem+json`, safe `title/detail`, `traceId`, `timestamp`, `correlationId`, and an `errors` extension keyed by stable camelCase field names. Keep controllers thin; implement through API behavior/problem-details configuration, not action-level checks. | Accepted | API | `Event.API.IntegrationTests`: missing required body property, invalid query binding, max-length binding failure, field-key/correlation assertions. |
| D-002 | Malformed JSON | Return HTTP 400 ProblemDetails with a body-level field key (`body`) and safe parse category. Never echo the raw payload or formatter exception text. | Accepted | API | Malformed object, truncated JSON, array sent to object endpoint, raw payload not reflected. |
| D-003 | Missing body | Return HTTP 400 ProblemDetails with stable `body` error key for empty, whitespace, or omitted bodies on endpoints requiring `[FromBody]` request DTOs. | Accepted | API | Empty body, whitespace body, omitted body with `application/json`. |
| D-004 | Wrong content type | Return HTTP 415 ProblemDetails for unsupported content types on JSON endpoints. Missing content type on an endpoint with a body is rejected consistently with the selected MVC/input-formatter behavior and documented by tests. | Accepted | API | `text/plain`, `multipart/form-data`, missing content type to JSON write endpoint, no raw body echo. |
| D-005 | Unknown JSON properties | Reject unknown JSON properties on write/admin/setup request bodies pre-v1. Prefer `System.Text.Json` unmapped-member rejection at the request-contract boundary; if a DTO legitimately needs extension data, it must opt in with an allowlist and tests. | Accepted | API/Application | Unknown property, server-owned property, mixed valid+unknown payload, explicit extension-data allowlist case if introduced. |
| D-006 | Over-posted server-owned fields | Server-owned fields are removed from request DTOs and are never trusted from the body. Because unknown properties are rejected, payloads containing `tenantId`, audit fields, status transitions, computed fields, HAL links, or authorization-only fields fail as bad requests unless a specific route explicitly owns that field. | Accepted | Application/API | Payload includes tenant id, created by/updated by, status, computed fields, `_links`, authorization-only fields. |
| D-007 | Oversized strings | Every external string has an explicit max length at the DTO/query/BFF boundary. Application validators remain authoritative and use `ValidateAsync`; model-state normalization handles binding-level size/format failures. Errors use stable field keys and do not include submitted values. | Accepted | Application | Boundary length, over limit by 1, very large payload, Unicode multi-byte cases, control-character cases. |
| D-008 | Invalid enum/model-binding failures | Invalid enum/model-binding failures return safe field-level ProblemDetails. String enums remain the public JSON contract; numeric unknown enum values are rejected for request bodies and query inputs where practical. | Accepted | API/Application | Invalid enum body, invalid enum query, numeric unknown enum, casing behavior, no internal enum dump beyond safe category/field. |
| D-009 | Public GET/query validation | Public/read queries are validated as external input. Query validators live at the API/Application request boundary for filter objects and high-risk scalar query groups; they must bound page size, date ranges, search length, cursor shape, sort/filter allowlists, module filters, and custom-property filters. Invalid public queries return safe 400 ProblemDetails without tenant/resource existence leaks. | Accepted | API/Application | Bad page size, bad cursor, bad sort, overlong search, invalid custom-property filter, Tenant B lookup id submitted in Tenant A context. |
| D-010 | Idempotency same key + same payload | Same key replay is valid only when tenant, authenticated principal category, HTTP method, route pattern/path, content type, and canonical request-body fingerprint match. Replay returns the original persisted eligible response and `X-Idempotency-Replay: true`. | Accepted | API/Persistence | Same tenant/key/body replay, same key equivalent JSON formatting, response header/body/status replay. |
| D-011 | Idempotency same key + different payload | Same key with different fingerprint, content type, route, or method is rejected with HTTP 409 ProblemDetails and stable code `idempotency_key_reuse`. Do not replay a response across different payloads or routes. This deliberately preserves the current repo/API contract documented in `docs/API.md`; the IETF draft examples use 422 for this case, so changing the status code would be a separate API migration. | Accepted | API/Persistence | Same key different body, different content type, different route, different method, no cross-tenant replay. |
| D-012 | Idempotency validation failure caching | Do not persist pre-execution model-binding, malformed JSON, missing body, unsupported content type, or Application validation 400 responses. A corrected retry with the same key may proceed if its fingerprint becomes valid. Persist only eligible post-execution responses under the existing size/content-type/5xx exclusions. | Accepted | API/Persistence | Validation failure retry not replayed, corrected retry with same key, oversized ProblemDetails not cached, 5xx not cached. |
| D-013 | BFF token boundary | Browser never receives access, refresh, or identity tokens. Browser-supplied auth/token/setup-secret headers are ignored or stripped where applicable; forwarding remains server-owned. | Accepted | Blazor/BFF | Serialized auth state, response bodies, logs, storage, proxy header stripping, client-supplied `Authorization`. |
| D-014 | BFF setup-secret exceptions | Setup-secret routes remain explicit bootstrap exceptions only. They require the BFF setup-secret resolver/source order, protected short-lived setup cookie/session where used, rate limiting, safe ProblemDetails, and no raw provider/setup-secret leakage. Browser `X-Setup-Secret` is never trusted. | Accepted | Blazor/BFF/API | Header spoofing, missing setup secret, invalid setup secret, stale setup cookie, raw provider error leakage. |
| D-015 | Upload proxy/session contract | Browser upload destination is never caller-controlled. BFF upload uses opaque session ids, trusted HTTPS presigned destination validation, owner binding, content-type binding, expiry checks, corrupt-payload rejection, and consume-once semantics after successful proxy upload. | Accepted | Blazor/BFF/Storage | Reuse, wrong user, content mismatch, arbitrary URL, expired/corrupt session, no presigned URL/token logging. |
| D-016 | Rich text default | User-authored rich HTML is disabled by default. `PublicExperienceHomeBlockKind.RichText` is treated as plain-text/configured-content until a sanitizer decision record exists. `EmailMessage.HtmlBody` is system-template-only; interpolated user values must be context-encoded before insertion. Any future user-authored rich HTML requires an approved server-side sanitizer profile, patch policy, and XSS regression tests. | Accepted | Application/UI/Security | Dangerous tags, attributes, protocols, SVG/math, markdown/raw transforms, encoded email interpolation, public-experience rendering as text. |
| D-017 | Validation telemetry | Validation telemetry may include endpoint/route, field name, validator code/category, length bucket, status, trace/correlation id, and safe tenant/resource ids only after authorization. It must not include raw input, request bodies, search terms, custom-property values, secrets, tokens, setup secrets, provider errors, presigned URLs, or arbitrary high-cardinality labels. | Accepted | API/Application/Observability | Log/metric assertions for raw payload/search/custom property/token/setup secret/provider errors/presigned URLs absent. |
| D-018 | Blazor UI-local validation scope | Blazor validation is UX and accessibility only. UI-local validators may cover required, max length, simple date ordering, URL/email shape, and client-only form composition. Authorization, tenant scope, uniqueness, capacity, quota, dynamic custom-property rules, module enablement, and persistence checks stay server-only and map back into `EditContext`. `Explore.Blazor.Client` must not reference `Explore.Application` validators directly. | Accepted | Blazor/Application | Server error mapping, no Application validator reference, focus/alert/status behavior, HAL-only action affordance gating. |
| D-019 | OpenAPI and generated client ownership | When API contracts change, the implementation agent owns OpenAPI/client regeneration using the documented repo commands, reviews generated diffs, and verifies generated clients compile. Required generation must not be delegated to the user as a task. Generated artifacts are never hand-edited. | Accepted | API/Blazor | OpenAPI generation command output, generated client diff review, Blazor client compile/test coverage for touched contract. |
| D-020 | Raw markup and `MarkupString` seams | `MarkupString` and other raw-rendering seams are allowed only for controlled markup or dynamic content that is proven encoded/sanitized before raw rendering. Prefer component composition and normal Razor encoding. `AiAssistantRail.razor` prompt-reference highlights now use `RenderFragment`/`RenderTreeBuilder.AddContent` instead of raw HTML. `ProjectionStatusSection.razor` status rows and `ExposureGovernanceSection.razor` flag headers no longer use `AddMarkupContent`; dynamic projection error text is rendered through `RenderTreeBuilder.AddContent`. `CommunityGuidelines.razor` remains a controlled `MarkupString` seam because tenant text is escaped before renderer-owned structural tags are emitted. Any new `MarkupString` or `AddMarkupContent` under `Explore.Blazor` or `Explore.Blazor.Client` must be deliberately reviewed and allowlisted. | Accepted | Blazor/Security | `AiAssistantRailTests.ReferenceHighlights_EncodeDangerousReferenceDisplayNames`; `CustomPropertyGovernanceTests.ProjectionStatus_EncodesDangerousLastErrorText`; `CommunityGuidelinesTests.Render_WhenGuidelinesContainDangerousHtml_EscapesTenantContent`; `BrowserInteropSafetyTests.BlazorSource_UsesRawHtmlRenderingOnlyInReviewedAllowlist`; continue tests for future raw DOM/JS seams. |
| D-021 | Public home rich-text blocks | `PublicExperienceHomeBlockKind.RichText` is currently plain/configured text, not user-authored rich HTML. The public home page must render block `Title`, `Subtitle`, and `Body` through normal Razor/component text content so Blazor encodes tenant content. Do not switch this to `MarkupString`, `AddMarkupContent`, markdown HTML, or JS DOM insertion without a new sanitizer decision and malicious-content tests. | Accepted | Blazor/PublicExperience/Security | `HomeTests.Home_OrganizationRichTextBlock_RendersTenantContentAsEncodedText` must keep proving `<script>`, `<img>`, and event-handler payloads stay text and do not create DOM nodes. |
| D-022 | Email HTML body composition | `EmailMessage.HtmlBody` is system-template HTML only. Fixed lifecycle templates may contain trusted renderer-owned tags, but every event title, organizer body, or future user/tenant value inserted into the HTML body must be context-encoded before `EmailDispatchOutbox.HtmlBody` persistence or SMTP send. Plain-text bodies may preserve raw text because they are not an HTML execution context. | Accepted | Application/Email/Security | `EventLifecycleEmailOutboxFactoryTests.CreateRegistrationConfirmation_HtmlBodyEncodesEventTitle`; `EventLifecycleEmailOutboxFactoryTests.CreateOrganizerNotification_HtmlBodyEncodesOrganizerBodyText`; future email-template work must add equivalent interpolation tests. |
| D-023 | Blazor upload UX and file metadata safety | Browser-side upload validation is UX-only. `IBrowserFile.Name`, `ContentType`, and `Size` are untrusted hints; BFF/API/Application remain authoritative for type, size, signature, ownership, and storage policy. Blazor upload and storage-display surfaces must not log raw browser filenames, display raw exception/provider/session details, or render storage-adjacent metadata as raw markup. Use encoded UI text/attributes, safe generic failures, and problem-details/code mapping where available. | Accepted | Blazor/BFF/Storage | `ImageStorageSupportServiceTests`, `ImageUploadClientTests`, `ImageStorageServiceTests`, `ImageStorageRecordClientTests`, and `CreateEventTests` cover current upload UX/error/log safety; `SharedComponentAccessibilityTests.StorageImage_RendersCustomAltAsAttributeOnly_WhenMetadataContainsMarkup`; `SharedComponentAccessibilityTests.StorageImage_RendersErrorTextAsEncodedText_WhenMetadataContainsMarkup`; future upload/display surfaces must add equivalent dangerous metadata coverage. |
| D-024 | Browser action JS interop | Blazor components must not use `eval`, string-built script snippets, or legacy global helpers for share, clipboard, scroll, or file-download browser actions. Browser capabilities flow through a typed interop service that imports an ES module and passes structured arguments to named functions. JS modules may use browser DOM APIs internally, but they must not accept HTML fragments, call `eval`, or log raw titles, URLs, filenames, or payloads. | Accepted | Blazor/Security | `BrowserActionInteropTests`; `BrowserInteropSafetyTests.BlazorSource_DoesNotUseEvalBasedJavaScriptInterop`; `BrowserInteropSafetyTests.BlazorSource_DoesNotUseDomHtmlInjectionSinks`; `BrowserInteropSafetyTests.BlazorSource_DoesNotUseLegacyGlobalDownloadInterop`; focused event UI tests for affected components. |
| D-025 | Shared-contact export format and artifact safety | Shared-contact export format is a fixed API contract: only `csv` and `tsv` are accepted, normalized to lowercase at the API boundary, and defensively revalidated by the Application handler. Blazor may normalize supported values for UX but must not be authoritative. Exported CSV/TSV cells that could be interpreted as spreadsheet formulas are neutralized before separator escaping, and generated filenames use bounded safe slugs rather than raw organization names. | Accepted | API/Application/Blazor/Security | `PublicQueryValidationTests` export-format cases; `ExportSharedContactsCommandHandlerTests.Handle_CsvFormat_SanitizesFormulaCellsAndFileName`; `ContactShareConsentServiceTests.ExportSharedContactsAsync_UppercaseFormat_NormalizesBeforeApiCall`; `ContactShareConsentServiceTests.ExportSharedContactsAsync_InvalidFormat_ReturnsNullWithoutCallingApi`. |
| D-026 | Storage provider diagnostic logging | Storage provider health checks, connection probes, and legacy S3 diagnostics may log bounded provider labels, status, and `FailureType` categories only. They must not log raw exception objects/messages, configured endpoints, bucket names, local filesystem paths, object keys, presigned URLs, access keys, secret keys, or provider response bodies. | Accepted | Infrastructure/Storage/Security | `S3FileStorageProviderTests.TestAsync_WhenBucketProbeFails_LogsFailureTypeWithoutRawProviderPayload`; `LocalFileStorageProviderTests.TestAsync_WithUnwritableRoot_LogsFailureTypeWithoutRawFilesystemPath`; `ObjectStorageServiceTests.TestConnectionAsync_WhenProbeFails_LogsFailureTypeWithoutEndpointOrProviderPayload`. |
| D-027 | Storage upload failure response details | Known storage upload failure codes are projected into API-owned canonical RFC 7807 `detail` and validation `errors` text. `CommandResponseResultMapper` must not echo `BaseCommandResponse.Message` or `Errors` for known storage upload codes because those values can contain provider diagnostics, object keys, policy details, tenant-scoped paths, or other lower-layer context. Unknown storage validation failures may continue through the generic command validation mapper until they are classified in the matrix. | Accepted | API/Storage/Security | `StorageUploadSessionControllerTests.UploadSessionContent_WhenProviderFailureContainsInternalData_ReturnsCanonicalProblemDetails`; `StorageUploadSessionControllerTests.UploadSessionContent_WhenValidationFailureContainsInternalData_ReturnsCanonicalValidationProblem`; existing `UploadSessionContent_WhenStorageFailure_ReturnsMappedProblemDetails`. |
| D-028 | Storage object metadata command failure HTTP mapping | Storage object metadata create/update command failures must return API-owned validation ProblemDetails, not `200 OK` responses containing `Success=false`. Controllers may map Application validation errors through the canonical command-validation mapper, but HTTP success status is reserved for successful metadata commands. | Accepted | API/Storage/Security | `StorageUploadSessionControllerTests.Create_WhenHandlerValidationFails_ReturnsValidationProblemDetails`; existing storage object route/body mismatch validation coverage. |
| D-029 | Storage object metadata update tenant authority | Storage metadata create/update commands must not use client-supplied DTO `TenantId` as authorization authority. Create authorization is collection-scoped and persistence derives tenant ownership from `ITenantContext`; update authorization is enriched from the persisted `StorageObject` identified by the route/body command id. The update handler must load the existing current-tenant entity, reject missing or wrong-tenant metadata as not found without side effects, patch only allowed metadata fields, and preserve persisted `TenantId`. Do not map update DTOs into fresh entities that could carry over-posted tenant authority. | Accepted | Application/Storage/Security | `StorageObjectCommandHandlerTests.CreateCommand_DoesNotExposeClientTenantIdAsAuthorizationContext`; `StorageObjectCommandHandlerTests.UpdateCommand_DoesNotExposeClientTenantIdAsAuthorizationContext`; `StorageObjectCommandHandlerTests.UpdateHandle_WhenDtoTenantIdDiffers_PreservesPersistedTenantAndAppliesAllowedFields`; `StorageObjectCommandHandlerTests.UpdateHandle_WhenStorageObjectIsOutsideCurrentTenant_ReturnsFailureWithoutUpdate`; `AuthorizationBehaviorTests.Handle_WithStorageObjectResource_EnrichesPersistedStorageAuthorizationContext`. |
| D-030 | Matrix-backed slice execution and boundary ownership | Remaining work must proceed by one high-risk matrix row or tightly related endpoint family at a time. Audit-only work is not progress unless it produces an updated matrix row, accepted/deferred decision, code/test change, or documented deferral with owner and rationale. API/Application remains authoritative for request and semantic validation; BFF validates only BFF-owned trust-boundary seams; Blazor validates UX and maps server errors; sanitization is seam-specific and never a global middleware/filter. | Accepted | Planning/API/Application/BFF/Blazor/Security | Each future slice must update `full-input-validation-sanitization-input-matrix.md`, this decision log if a new contract is needed, and `full-input-validation-sanitization-tasks.md` with focused verification evidence before claiming completion. |
