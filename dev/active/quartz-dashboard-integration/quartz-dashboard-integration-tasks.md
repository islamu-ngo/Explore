## Defects Found And Fixed During Self-Review

Both were found by re-reading the implementation against its own stated invariants, not by a failing test.

1. **Job rows advertised controls on a read-only host.** `SchedulerAdminJobCollectionLinkPolicy` gated only on job
   state, while the read-only check lived on the overview DTO. A read-only host would have hidden the scheduler
   pause/resume buttons but still rendered per-job trigger/pause/resume, which the command handlers then refuse —
   exactly the advertise/accept mismatch the design exists to prevent. Fixed by injecting `ISchedulerAdminPolicy`
   into the per-row policy. Regression test: `JobLinks_WhenHostIsReadOnly_OmitEveryControlAffordance`.
2. **The dashboard could mount without a scheduler.** Quartz services are registered by
   `ApiHostServiceCollectionExtensions` only when the selected email-dispatch mode is Quartz, so
   `Scheduler:Quartz:Enabled=true` alone does not guarantee an `ISchedulerFactory` exists. `DashboardEnabled=true`
   with a non-Quartz dispatch mode would have mounted a dashboard whose pages fail on first render. Fixed by
   checking the container for a registered `ISchedulerFactory` at map time — asking reality rather than restating
   the host's conditions, which would drift — and logging a warning explaining why it was skipped.

Also tightened: the five write actions now declare `409 Conflict` in `[ProducesResponseType]`, so the refusal path
is part of the published contract rather than an undocumented runtime behaviour.

## Remaining / Deferred Work

- **Full-suite regression:** `Event.API.IntegrationTests` full run was in progress at handoff; scheduler-scoped subsets all passed.
- **Dashboard behaviour under a live scheduler:** the dashboard is excluded in the `Testing` environment (as the scheduler itself is), so integration tests assert composition and route ownership, not rendered dashboard pages. Rendering was proven out-of-tree in a scratchpad probe.
- **Job authoring** (create/delete jobs, reschedule/unschedule triggers, calendars, execution history): not exposed by the first-party API, and this is a design boundary rather than a backlog item. Jobs here are code-defined in `RegisterRecurringJobs`/`RegisterMaintenanceSweeps` and their cadence is settings-defined and re-registered from configuration on every boot, so a UI reschedule would contend with startup registration and could be silently reverted. Cadence changes belong in the existing settings sections. Standalone operators who need ad-hoc authoring enable the upstream dashboard.
  - *Note:* recovery actions were originally bundled into this bullet and have since been implemented as Phase 4 — see Decision I. Recovery and authoring are different concerns and should not be deferred together.
- **Clustering UI visibility:** the overview already returns `clustered`; add node-level detail when clustering is proven (P0.3 in the Quartz report).
- **Localization:** admin tooling is English-only, unchanged by this workstream.
