# API Changelog

## Breaking Change Evidence

Intentional breaking API changes must add an entry to this file in the same PR that changes `schemas/openapi.json`, `docs/API_CONTRACT_INVENTORY.md`, or `Explore.Blazor.Client/Clients/EventApiClient.g.cs`.

Each breaking-change entry must include:

- affected route, operation, schema, or generated client method;
- old behavior and new behavior;
- affected clients or operator workflows;
- migration guidance or compatibility window;
- release version or target milestone;
- link to retained OpenAPI contract evidence from `openapi-contract-guard` when available.

Non-breaking additive changes may be summarized in the current-mainline section, but removals, renamed operations, authentication/authorization contract changes, response shape changes, problem type changes, pagination/cursor changes, and generated-client breaking changes need explicit evidence here.

## Current Mainline (API version `0.1`)

Key behavior in current code:

- Media-type API versioning (`Accept: application/json;v=0.1` or `application/hal+json;v=0.1`).
- HAL responses with `Prefer: return=minimal` support.
- Output caching policies (`LookupData`, `ListData`, `DetailData`) and HybridCache usage.
- ETag middleware for successful JSON/HAL `GET` responses with `304 Not Modified` support.
- Security headers middleware (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy`).
- Additive optional managed-mode upgrade assessment contract: authenticated Control Plane callers with the dedicated `event-management:read` machine scope can send bounded JSON bodies to `POST /api/management/upgrade/preflight` / `EvaluateManagementUpgradePreflight` and `POST /api/management/upgrade/postflight` / `VerifyManagementUpgradePostflight`. Preflight reports Event-owned deployment mode, current/target semantic versions, management API compatibility, registration and directional-credential freshness, bootstrap completion, aggregate readiness, and stable blocker codes without changing Event state. Postflight verifies the expected Event and management API versions against the same bounded evidence. Managed mode remains disabled by default, no private Control Plane dependency is introduced, and upgrade execution remains outside Event. Generated clients use `EvaluateManagementUpgradePreflightAsync(ManagementUpgradePreflightRequest, ...)` and `VerifyManagementUpgradePostflightAsync(ManagementUpgradePostflightRequest, ...)`.
- Additive managed tenant preflight contract: registered Control Plane callers with the dedicated `event-management:read` machine scope can send the strict versioned provisioning request to `POST /api/management/tenants/preflight` / `EvaluateManagedTenantProvisioningPreflight`. The side-effect-free `200 OK` assessment reports normalized request hash, Event and management API versions, managed/Event instance identity, persisted deployment mode, registration state, stable blocker codes, conditional MultiTenant capacity, resolved immutable plan quotas, accepted modules/domain/branding/settings intent, and assessed correlation. SingleTenant or unconfigured-capacity instances return typed blockers with no capacity snapshot; malformed or unknown request members return `400`. The assessment is explicitly provisional because scheduling rechecks mode, capacity, slug, domain, catalog, and setting policy under its mutation lock. The route uses the managed read credential, authenticated rate policy, and Control Plane timeout and never creates an operation, outbox/audit row, tenant, or provider call. Generated clients use `EvaluateManagedTenantProvisioningPreflightAsync(ManagementTenantProvisioningRequest, ...)`.
- Additive managed tenant provisioning contract: a registered managed instance authenticates with the dedicated `X-Control-Plane-Key` scheme and can schedule Event-owned tenant creation through `POST /api/management/tenants/provision` / `ScheduleManagedTenantProvisioning` (`202 Accepted`), read safe operation state through `GET /api/management/tenant-provisioning/{operationId}` / `GetManagedTenantProvisioningOperation`, and cancel a still-pending operation through `POST /api/management/tenant-provisioning/{operationId}/cancel` / `CancelManagedTenantProvisioningOperation`. Scheduling is available only for persisted `MultiTenant` instances with configured capacity, is idempotent by managed-instance plus external request id and canonical request hash, and writes the bounded request snapshot plus an internal outbox pointer atomically under the deployment-mode lock. Execution rechecks persisted mode under the same lock before tenant mutation; terminal outbox failure reconciles the operation to a redacted failed state. Event does not call Coolify or any private Control Plane infrastructure provider. Managed mode remains disabled by default; read/write policies and write rate limits are published in OpenAPI through the dedicated api-key security requirement.

- Correlation ID propagation (`X-Correlation-ID`/`X-Request-ID`) and structured request logging.
