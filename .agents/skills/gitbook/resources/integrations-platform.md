# GitBook Integrations Platform

A guide for building integrations on GitBook's developer platform: apps running inside GitBook that render custom editor blocks, display configuration UIs, listen to events, and authenticate with external services via OAuth.

## Mental Model & Constraints

Integrations are TypeScript applications executed by GitBook's runtime, subject to three fundamental constraints:
1. **Server-Side Backend Rendering**: Your component's `render` function runs on GitBook's backend on every interaction and returns ContentKit markup (a JSX-like UI description). There is no client-side DOM access or React tree.
2. **No Arbitrary Script Injection**: The GitBook runtime strictly forbids injecting raw client-side JavaScript or `<script>` tags into published documentation pages. Integrations interact via custom blocks, webframes, and events.
3. **Local Development is a Reverse Proxy**: Running `gitbook dev` does not spin up a standalone web server you visit in a browser; it proxies traffic from an installed integration in `app.gitbook.com` back to your local machine.

## Project Structure & Manifest

Scaffold a new integration via CLI: `gitbook new <dir>`.
```
my-integration/
├── gitbook-manifest.yaml   # Identity, scopes, blocks, configuration schema
├── .gitbook-dev.yaml       # Local dev configuration (generated by gitbook dev)
├── package.json
└── src/
    └── index.tsx           # Entrypoint exporting createIntegration()
```

### Manifest Essentials (`gitbook-manifest.yaml`)
Requires `name` (globally unique), `title`, `description`, `organization`, `visibility`, `scopes`, and `script`.
- Declare installer settings forms under `configurations:`.
- Declare environment secrets via `${{ env.SECRET_KEY }}` references (never commit raw secrets).
- See [integration-manifest.md](integration-manifest.md) for full schema specifications.

## Defining Custom Blocks

A custom block appears in the GitBook editor insert palette (⌘ + /) **only when declared in both places**:
1. Declared in `gitbook-manifest.yaml` under `blocks:`.
2. Implemented in code via `createComponent` with a matching `componentId`.

```tsx
import { createIntegration, createComponent } from '@gitbook/runtime';

const statusBlock = createComponent({
  componentId: 'service-status',
  initialState: { status: 'Operational' },
  action: async (element, action, context) => {
    if (action.action === 'refresh') {
      return { state: { status: 'Checking...' } };
    }
    return {};
  },
  render: async (element, context) => (
    <block>
      <card title="Service Status">
        <text>{element.state.status}</text>
        <button label="Refresh" onPress={{ action: 'refresh' }} />
      </card>
    </block>
  ),
});

export default createIntegration({
  components: [statusBlock],
  events: {
    space_content_updated: async (event, context) => {
      // React to content updates
    },
  },
});
```

## The Development Loop

The GitBook integration workflow has an unexpected order: **publish once before local development**:
1. **Prerequisites**: Node 18+, personal access token, and `@gitbook/cli`: `npm install -g @gitbook/cli && gitbook auth`.
2. **Publish Once**: Run `gitbook publish` in the root directory. This registers the integration privately and outputs an install link.
3. **Install**: Open the link and install the integration into at least one space. `gitbook dev` requires an installed instance.
4. **Develop**: Run `gitbook dev`. All traffic from your installed integration is proxied to your local code. Interact with it inside `app.gitbook.com`.
5. **Re-publish**: Run `gitbook publish` to release updates.

## Runtime & ContentKit

- **HTTP Handlers**: Handle external webhooks or API requests via `fetch` export.
- **GitBook Events**: Listen to `space_content_updated`, `space_view`, `space_gitsync_completed`, etc.
- **ContentKit UI**: Visual component vocabulary including layout (`block`, `vstack`, `hstack`), display (`card`, `text`, `markdown`), and interactive elements (`button`, `textinput`, `select`, `modal`, `webframe`).
- **External OAuth**: Built-in `createOAuthHandler` helper.

See [contentkit.md](contentkit.md) and [integration-runtime.md](integration-runtime.md) for complete component catalogs, event signatures, and OAuth recipes.
